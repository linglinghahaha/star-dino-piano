## Child-facing Note Language

The current display rule is authoritative across every chapter:

- planning notation such as `Do/C` means the teaching relationship between solfege and letter name; it does **not** authorize a literal dual label in the child-facing game;
- visible keyboard labels, task/target cards, parts, route pads, staff hints, locators, feedback, effects, results, map labels, and garden objects use letter names only: `C D E F G` (later `A B` under their own entry gates);
- only a small-dinosaur dialogue bubble may visibly use `Do Re Mi Fa Sol`; that dialogue may connect the channels with a sentence such as `我唱 Do，你来弹 C`;
- gated parent evidence may retain dual identity such as `C / Do`; child-facing accessibility descriptions use letter names only and may add a non-answer keyboard locator;
- hidden listening/check states override every naming allowance: the current target must not leak through visible text, ARIA, title, alt text, classes, color, motion, or a highlighted key before the child responds.

`14_NOTE_IDENTITY_MATRIX.md` owns this carrier policy. Older screenshots, historical gate logs, or lesson shorthand that contain `Do/C` remain historical evidence, not the current UI specification.

Shared-file rule:

- `README`, `08`, `16`, `18`, `23`, `25`, and `26` may contain several owners' status, but each task edits only its scoped rows and confirms that another task is not actively editing the same file.
- The curriculum task specifies what a scene/action must communicate; the prototype task chooses and polishes the actual UI, animation, audio, and bitmap asset that satisfies it.
- The animation/audio task creates traceable source concepts and candidates; the prototype task owns conversion into runtime assets and integration after coordinator approval.
- If implementation exposes a conflict, the prototype task reports the exact level, field, and reason. It must not resolve the conflict by silently changing curriculum semantics.
- If curriculum changes an already implemented contract, it records the affected ids and asks the prototype task to rerun the relevant teaching and visual gates.
- The coordinator requires branch self-review, then independently reads evidence before issuing a pass/return decision. Status uses `passed`, `partial`, `missing`, or `contradicted`; screenshots and automation never substitute for real-device, consent, or child-observation evidence.

Every curriculum-to-prototype handoff must provide:

1. level id, prerequisite, and one new teaching axis;
2. exact pitch/register and note order;
3. opening story problem and visible success consequence;
4. initial cue, reduced cue, and wrong-answer reveal;
5. child action, automatic transition, and natural stop point;
6. played/stable/retained evidence rule and forbidden mastery claims;
7. touch, MIDI, and microphone capability limits;
8. pacing fields from `docs/33`: primary game verb, meaningful-input budget, world-change frequency, achievement kind, anti-boredom role, and natural rest;
9. non-reading equivalent for every child-facing text clue;
10. required character gesture, scene object, voice line, and audio event, described as a requirement rather than a finished asset.

The prototype task returns:

1. implemented ids and any deliberate deviations;
2. screenshots or recordings for initial, correct, wrong, recovery, completion, and rest states;
3. input-route and regression results;
4. any child-observation evidence and adult interventions;
5. unresolved curriculum questions, without inventing replacement rules.
